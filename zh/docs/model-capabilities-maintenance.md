# 模型能力维护

本项目将模型能力解析视为一个分层系统：

1. 来自连接提供商的运行时元数据
2. `models.dev` 捆绑/运行时快照数据
3. 显式的兼容性别名
4. 启发式回退作为最后手段

## 内部策略

- 内置的 OmO 代理/类别要求模型必须使用规范的模型 ID。
- 别名仅为了保持与历史 OmO 名称或提供商特定的修饰名称的兼容性而存在。
- 当规范的模型 ID 加上结构化设置可以表达相同的内容时，不应将像 `-high`、`-low` 或 `-thinking` 这样的新修饰名称添加到内置要求中。
- 如果提供商或配置输入仍在使用别名，请在边缘将其规范化，并在内部继续使用规范 ID。

## 添加别名时

- 将别名规则添加到 `src/shared/model-capability-aliases.ts`。
- 包含为什么存在该别名的基本原理。
- 添加或更新测试，以便明确覆盖该别名。
- 确保别名规范目标存在于捆绑的 `models.dev` 快照中。

## 护栏

`bun run test:model-capabilities` 强制执行以下不变量：

- 精确的别名目标必须存在于捆绑的快照中
- 精确的别名键不能悄悄变成规范的 `models.dev` ID
- 模式别名不得重写规范的快照 ID
- 内置要求模型必须保持规范并以快照为后盾

计划的 `refresh-model-capabilities` 工作流在打开自动快照刷新 PR 之前运行这些护栏。
